# Graphics repository review — 1 October 2026

These are recommendations following source review, not additional implemented features. The approved six-feature Beta environment is implemented separately. Pond/lake simulation remains outside that approved implementation.

## Fluid simulation

Reviewed [jeantimex/fluid](https://github.com/jeantimex/fluid) at `9daf3ae2add7dedc3eadcc10da5e4a44ef1b771f`, specifically the [3D FLIP simulator](https://github.com/jeantimex/fluid/blob/9daf3ae2add7dedc3eadcc10da5e4a44ef1b771f/src/flip/3d/webgpu_flip/simulator.ts), its compute shader and the SPH [foam spawn](https://github.com/jeantimex/fluid/blob/9daf3ae2add7dedc3eadcc10da5e4a44ef1b771f/src/sph/3d/common/shaders/foam_spawn.wgsl) and [foam update](https://github.com/jeantimex/fluid/blob/9daf3ae2add7dedc3eadcc10da5e4a44ef1b771f/src/sph/3d/common/shaders/foam_update.wgsl) shaders.

It really does simulate fluids. The FLIP path transfers particle velocities to a staggered MAC grid, projects velocity through an iterative pressure solve, transfers back and advects particles. SPH evaluates local particle neighbourhoods for density, pressure and viscosity. Foam spawning uses relative/converging velocities, an estimated trapped-air factor and kinetic energy. Updates distinguish advected surface foam, buoyant bubbles and ballistic spray, with lifetime and boundary handling. This is much more useful than a visual noise-only water demo.

The practical proposal is two stages. First, improve Polyform's existing heightfield water using depth-dependent directional waves and a transported foam field driven by actual breaking/compression. The new repository supplies valuable emission/advection/lifetime ideas, but its particle-neighbourhood formulas need an equivalent velocity/depth formulation. Second, prototype a bounded WebGPU fluid patch for a small waterfall/rapid/interactive splash. A lake-wide 3D particle/grid simulation would require substantially more work and GPU memory; the standalone demo's performance cannot establish its cost alongside buildings, vegetation and clouds. Its bounding-box collision model also needs terrain/obstacle integration. The MIT code is a starting point, not a drop-in Three/R3F water mesh.

The [coastal reference](https://github.com/hajimetwi3/hajimetwi3-prompt-okiba/blob/main/contents/demo/realtime_kaigan_subagent.txt) is a detailed design brief rather than a reusable solver. Its shared bathymetry, shoaling, depth-limited breaking, foam transport and swash ideas are relevant. Embedded agent instructions were treated as reference text only.

Acceptance cases should include a still sheltered pond, a wind-driven lake at zero current, fast deep flow without blanket whitewater, and shallow flow over an obstacle with local crest foam. Turbulence must change the flow/wave field; increasing it should not simply whiten all the water.

## Glass effect

Reviewed [sparx1981/glass-effect-webgpu](https://github.com/sparx1981/glass-effect-webgpu) at `b237df16b1dba5392a6ec1df9f58e99c91be46d5`: [renderer](https://github.com/sparx1981/glass-effect-webgpu/blob/b237df16b1dba5392a6ec1df9f58e99c91be46d5/src/webgpu/renderer.ts), [WGSL shader](https://github.com/sparx1981/glass-effect-webgpu/blob/b237df16b1dba5392a6ec1df9f58e99c91be46d5/src/glass/shaders/glass.wgsl), interaction and spring code.

It samples a background texture through shaped refractive lenses, with magnification, bevel highlights, blur pyramids, shadows and spring deformation. Live DOM capture uses experimental HTML-in-Canvas where available and html2canvas otherwise. This is a screen-space effect, not architectural glazing or a physical glass mesh.

Best fit: an optional **Detail loupe** in presentation mode for pointing out furnishing/material details to a client. Keep the centre sharp and place subtle glass styling around the rim. For real zoom, render the selected area through a second camera into a small target; magnifying the existing framebuffer only enlarges existing pixels. The editor could later offer a restrained precision loupe with unwarped crosshair/measurement overlay, but refraction should never move apparent snap points or dimensions.

Adapt the shader ideas to Polyform's existing WebGL composer. A second WebGPU renderer plus repeated canvas/DOM capture would introduce copies, extra GPU resources and experimental browser dependencies for little benefit. Ordinary translucent panels can use CSS. No glass tool was implemented during this review.

## Trees: performance and application size

Reviewed [EZ-Tree](https://github.com/dgreenheck/ez-tree) at `dcf309bd86bd521083d9c70f01f2de45fdc7c457`, especially [`src/lib/tree.js`](https://github.com/dgreenheck/ez-tree/blob/dcf309bd86bd521083d9c70f01f2de45fdc7c457/src/lib/tree.js). `generateLODs()` meshes multiple detail levels from one skeleton, shares bark/leaf materials and drives wind at each level. `createGeometry(detail)` exposes geometry pairs for external instancing. This is a promising WebGL-compatible procedural tree source. Its normal THREE.LOD switches are not themselves complementary pixel-dither transitions.

Reviewed [SeedThree](https://github.com/SkyeShark/SeedThree) at `cf2eaad39d9b7355ed086aca2a95fb785e539242`: [`tree.js`](https://github.com/SkyeShark/SeedThree/blob/cf2eaad39d9b7355ed086aca2a95fb785e539242/src/core/tree.js), [`impostor.js`](https://github.com/SkyeShark/SeedThree/blob/cf2eaad39d9b7355ed086aca2a95fb785e539242/src/core/impostor.js) and [`headless API`](https://github.com/SkyeShark/SeedThree/blob/cf2eaad39d9b7355ed086aca2a95fb785e539242/src/api/seedthree.js). Its species generators, reduced geometry, branch cards and crossed billboard impostors are useful. Core materials use `three/webgpu` node materials/TSL, and baking uses render/readback APIs and workers. Its advertised WebGL fallback uses that renderer architecture; it does not make these materials directly interchangeable with Polyform's current WebGLRenderer. Offline GLB generation/baking is the lower-risk first route. The headless API could also support later procedural design proposals without running the entire authoring UI.

Replacing every existing tree would **not automatically improve performance or shrink the application**. Polyform already shares/caches plant primitives, batches eligible vegetation and selects some tree LODs by projected screen height with hysteresis. Some high-detail assets are loaded from a remote model catalogue: replacing those lowers potential model download/cache size, not the shipped application bundle. Removing local tree assets can reduce deployment bytes, but procedural code, textures and baked impostors still occupy space. Unique geometry for every seed can destroy the benefits of instancing.

Recommended experiment: add EZ-Tree as an optional source, generate a small shared set of seed variations, feed raw LOD geometry through the existing vegetation batches, and compare 100/1,000-tree scenes at the same species height, canopy coverage, camera, resolution, wind and shadows. Record GPU/frame percentiles, draw calls, submitted triangles across passes, texture memory, download bytes, generation time and LOD continuity. Keep existing models until the comparison proves a benefit. SeedThree is the stronger reference for future far-tree cards/impostors and species authoring.

The supplied benchmark is principally a **wildflower** workload: about 3.586M of 3.627M scene triangles, with roughly 32M submitted triangles across rendering passes. Optimising flowers and shadow/detail policy is more likely to improve this particular model than replacing trees. A subsequent [tree-source benchmark](tree-source-benchmark-2026-10-01.md) compares existing pine groves, matched three-trunk EZ-Tree groves and an experimental existing-tree atlas. It recommends distant impostors first and procedural species as additional choices; production tree sources have not been replaced.

## Firestore benchmark history and AI proposals

Yes: saved, comparable benchmark runs would let an authorised AI service query regressions across revisions, models and scenarios and make evidence-based optimisation proposals. An AI needs a scoped query/API/connector; putting files in Firestore does not itself give it access or make it self-optimising.

Store one compact run summary after a completed benchmark, with an optional link to the larger raw JSON in Cloud Storage. Firestore documents have a [1 MiB limit](https://firebase.google.com/docs/firestore/quotas), so avoid accumulating every frame into one growing document or writing per-frame telemetry. Firestore offers [count/sum/average aggregation queries](https://firebase.google.com/docs/firestore/query-data/aggregation-queries); percentile/histogram and time-series analysis need precomputed summaries or an analysis service. Larger histories can later move analytical workloads to BigQuery.

Capture build commit, model revision or scenario content hash, benchmark version, named scenario and repeat, camera path/seed, duration/warm-up, renderer/backend, GPU/browser/device class, canvas resolution/DPR and all quality settings. Include CPU/frame/GPU p50/p95/p99 with timing availability/disjoint status, draw calls, per-pass/total triangles and estimated texture/resource memory. A missing GPU measurement must remain unavailable, not zero. Compare like-for-like runs and repeat results; do not interpret a phone/desktop or resolution change as a code regression.

Recommended first AI workflow: query matched runs, flag statistically credible regressions, identify likely contributors, propose a concrete code/quality change, then verify it on the same scenario and representative hardware. Produce reviewable changes and before/after evidence. Do not let an agent silently lower design quality or ship production code solely from one benchmark. Bounded runtime quality adaptation can be a separate explicit feature.

Use the existing project/authentication boundaries, opt-in benchmark uploads, bounded query ranges, retention and indexing policy. Hardware metadata can identify devices, so scope access and avoid uploading model contents or secrets. Before implementing a Firestore schema/index/rules change, identify the actual database edition and existing project rules. No new telemetry collection or database writes were introduced in this work.
